今天是我第一次接触 OpenHarmony、STM32 和无人车开发。在此之前，我对嵌入式开发几乎一无所知，原本以为只要安装一个编程软件就可以开始写代码。

## 二、认识无人车开发环境

课程中的无人车并不是普通的软件项目，而是由多个部分共同组成的嵌入式系统，主要包括：

- **Windows**：运行 VS Code、Keil MDK、ST-LINK Utility 和串口助手。
- **Ubuntu 虚拟机**：保存和编译 OpenHarmony 源码。
- **SSH**：让 Windows 上的 VS Code 远程连接 Ubuntu。
- **Hi3861**：负责 OpenHarmony、Wi-Fi 和网络通信。
- **STM32**：负责灯光、串口、传感器及其他硬件控制。
- **开发板与传感器**：最终组成能够实际运行的无人车。

我现在理解到，编写代码只是整个开发过程中的一个环节。程序要在无人车上真正运行，需要经过以下步骤：

```text
编写代码
    ↓
编译程序
    ↓
生成 HEX 文件或固件
    ↓
将程序烧录到开发板
    ↓
复位开发板
    ↓
观察程序运行结果
```

## 三、搭建 OpenHarmony 开发环境

今天我使用的是 **Windows + Ubuntu 虚拟机** 的混合开发方式。

Windows 主要作为操作界面，Ubuntu 负责存放和编译 OpenHarmony 源码，两者通过 SSH 建立连接。

在配置过程中，我学习了几个以前没有接触过的 Linux 命令：

```bash
pwd
whoami
ls
cd
find
hostname -I
```

这些命令的作用如下：

| 命令 | 作用 |
|---|---|
| `pwd` | 查看终端当前所在目录 |
| `whoami` | 查看当前登录用户 |
| `ls` | 查看当前目录中的文件 |
| `cd` | 切换目录 |
| `find` | 查找文件或文件夹 |
| `hostname -I` | 查看 Ubuntu 虚拟机的 IP 地址 |

### 1. 查找 OpenHarmony 源码

我在查找 `code-1.0` 时，输入命令后出现了以下错误：

```text
find: unknown predicate '-namecode-1.0'
```

后来我才明白，Linux 命令中的空格也是语法的一部分，`-name` 和 `"code-1.0"` 之间必须保留空格。

正确的命令是：

```bash
find ~ -type d -name "code-1.0"
```

最终确认源码并没有丢失，而是存放在：

```text
/home/harmony/harmony/code/code-1.0
```

之前 VS Code 打开的是：

```text
/home/harmony/code
```

这是另一个空目录，因此无法看到源码。

这次问题让我认识到：

> 编辑器当前打开的文件夹与终端当前所在的目录是两件不同的事情。

## 四、学习 SSH 远程连接

今天还遇到了 VS Code 无法再次连接 Ubuntu 的问题。

我了解到，Ubuntu 虚拟机通常通过 DHCP 自动获取 IP 地址。虚拟机重启以后，IP 地址有可能发生变化，导致原来的 SSH 配置无法继续连接。

可以在 Ubuntu 中执行以下命令查看当前 IP 地址：

```bash
hostname -I
```

也可以使用：

```bash
ip a
```

然后在 Windows 中测试网络是否连通：

```powershell
ping 虚拟机IP地址
```

再测试能否通过 SSH 登录：

```powershell
ssh harmony@虚拟机IP地址
```

我还学习了如何检查 Ubuntu 的 SSH 服务：

```bash
sudo systemctl status ssh
```

只有看到以下内容，才说明 SSH 服务正在正常运行：

```text
active (running)
```

如果 SSH 服务没有运行，可以执行：

```bash
sudo systemctl restart ssh
```

通过今天的操作，我初步理解了下面的连接关系：

```text
Windows 上的 VS Code
        ↓
       SSH
        ↓
Ubuntu 虚拟机
        ↓
OpenHarmony 源码与编译环境
```

## 五、认识 Python 与 OpenHarmony 编译

OpenHarmony 的 `code-1.0` 工程中包含一个 `build.py` 文件，需要在 Ubuntu 终端中通过 Python 执行。

我一开始以为需要在 Windows 中重新配置 Python，后来才明白：源码位于 Ubuntu 中，所以真正参与编译的是 Ubuntu 里的 Python，而不是 Windows 里的 Python。

可以使用以下命令检查 Python 环境：

```bash
python --version
python3 --version
```

进入正确的源码目录：

```bash
cd /home/harmony/harmony/code/code-1.0
```

确认当前目录中存在 `build.py`：

```bash
ls build.py
```

然后执行编译：

```bash
python build.py wifiiot
```

如果提示找不到 `build.py`，不一定是 Python 安装错误，更可能是终端没有进入 `build.py` 所在的目录。

这让我学会了：看到报错时不能只关注“程序运行失败”，还要判断它究竟属于哪一种问题：

- 程序代码问题；
- 软件环境问题；
- 文件路径问题；
- 命令输入问题；
- 工具版本问题。

## 六、完成 STM32 串口与流水灯实验

除了搭建环境，我还尝试修改了 STM32 无人车的 `main.c`。

本次实验的目标是：

1. 小车复位后通过串口输出 `hello world`。
2. 电脑通过串口发送大写 `HELLO`。
3. STM32 收到完整指令后，让左右两侧的六颗 WS2812 灯同步流水。

### 1. 认识变量

程序中使用了两个变量：

```c
u8 i;
u8 pos = 1;
```

其中：

- `u8` 表示无符号 8 位整数。
- `i` 用来依次处理第 1～6 颗灯。
- `pos` 用来记录当前应该点亮的位置。
- `pos` 的初始值是 `1`，表示先点亮第一颗灯。

### 2. 判断是否收到串口指令

```c
if (USART_RX_STA == 1)
```

这段代码表示：只有串口接收到完整的 `HELLO` 后，程序才会执行灯光控制代码。

因此，小车刚开机时不会自动流水。只有电脑发送正确的指令以后，灯光效果才会开始。

### 3. 依次处理六颗灯

```c
for (i = 1; i <= 6; i++)
```

这段循环会依次处理：

```text
第1颗 → 第2颗 → 第3颗 → 第4颗 → 第5颗 → 第6颗
```

程序判断当前处理的灯是否为需要点亮的位置：

```c
if (i == pos)
```

如果相等，就把左右两边对应位置的灯设置为白色：

```c
L_ws2812_rgb(i, WS_WHITE);
R_ws2812_rgb(i, WS_WHITE);
```

其他位置的灯设置为熄灭：

```c
L_ws2812_rgb(i, WS_DARK);
R_ws2812_rgb(i, WS_DARK);
```

完成颜色设置后，还需要刷新灯带：

```c
L_ws2812_refresh(led_num);
R_ws2812_refresh(led_num);
```

前面的 `rgb()` 函数只是修改灯光数据，执行 `refresh()` 后，灯光变化才会真正显示出来。

### 4. 实现循环流水

每完成一次灯光更新，就让当前位置加一：

```c
pos++;
```

当位置超过第六颗灯时，重新回到第一颗：

```c
if (pos > 6)
{
    pos = 1;
}
```

因此，灯光位置会按照下面的顺序变化：

```text
1 → 2 → 3 → 4 → 5 → 6 → 1 → 2……
```

程序中的：

```c
delay_ms(100);
```

表示每隔 100 毫秒移动一次。

如果将数值改小，流水速度会变快；如果将数值改大，流水速度会变慢。

## 七、理解无限循环问题

课程原来的灯光函数中使用了：

```c
L_runingled();
```

这个函数内部存在持续循环。一旦程序进入该函数，就不会正常返回主循环，因此程序很难继续处理其他任务，也无法通过新的串口指令轻松关闭灯光。

为了让左右两边的灯同时流水，更合理的做法是在主循环中每次只更新一步灯光，而不是直接进入一个无法退出的流水灯函数。

这让我初步认识到，嵌入式程序不能只考虑“功能能不能运行”，还要考虑：

- 函数会不会返回；
- 主循环是否还能继续执行；
- 串口是否还能接收新命令；
- 灯光效果能否停止或切换；
- 是否会因为无限循环阻塞其他功能。

## 八、学习编译、烧录与串口调试

今天我第一次完整接触了 STM32 程序从代码到硬件运行的过程：

```text
Keil 修改代码
    ↓
Ctrl + S 保存代码
    ↓
按 F7 编译程序
    ↓
生成 Template.hex
    ↓
ST-LINK Utility 执行 Program & Verify
    ↓
复位或重新启动小车
    ↓
使用串口助手观察运行结果
```

### 1. 编译不等于烧录

我曾经修改了：

```c
printf("hello world\r\n");
```

但是串口中仍然显示旧内容。

这说明：

> 修改并编译代码，不代表新的程序已经进入开发板。

必须在 ST-LINK Utility 中重新选择最新生成的 HEX 文件，然后执行：

```text
Target → Program & Verify → Start
```

等待出现烧录和校验成功的提示后，新程序才真正进入 STM32。

### 2. 串口参数

串口助手使用的主要参数为：

```text
端口：COM3
波特率：115200
数据位：8
停止位：1
校验位：NONE
```

串口助手应该先打开，再复位或重新启动小车，这样才能看到程序启动时发送的：

```text
hello world
```

### 3. 字符串区分大小写

程序识别的是：

```text
HELLO
```

如果发送：

```text
hello
```

就不会触发流水灯。

这让我认识到，C 语言中的字符串比较通常区分大小写。对于程序来说，`HELLO` 和 `hello` 是两个不同的字符串。

## 九、认识 Keil 注释与编码问题

在 Keil MDK 中，C 语言注释可以写成：

```c
// 单行注释
```

或者：

```c
/*
多行注释
*/
```

但是旧版本 Keil 对 UTF-8 中文支持不好，从其他软件中复制中文注释后可能出现乱码。

乱码通常只影响注释显示，不会影响程序运行。

为了减少编码问题，可以优先使用英文注释：

```c
u8 i;          // LED index
u8 pos = 1;    // Current LED position
```

如果必须使用中文，可以考虑将文件通过 GBK 编码保存，但需要避免随意改变整个旧工程的编码格式。

## 十、今天遇到的主要问题

今天遇到的问题主要包括：

1. 把空目录误认为 OpenHarmony 源码目录。
2. Linux 命令漏写空格。
3. 不理解终端目录与编辑器目录的区别。
4. 虚拟机 IP 变化导致 SSH 连接失败。
5. 分不清 Windows Python 和 Ubuntu Python。
6. 没有进入正确目录就执行 `build.py`。
7. 编译后没有重新烧录，导致开发板仍然运行旧程序。
8. 发送了小写 `hello`，但程序等待的是大写 `HELLO`。
9. 调用了带无限循环的灯光函数，导致程序无法继续处理其他任务。
10. Keil 中的中文注释出现乱码。
11. 编译出现 warning 后，不知道应该根据警告行号继续检查代码。

这些问题看起来比较零散，但它们分别涉及目录、命令、网络、编译、烧录、串口和代码逻辑，是嵌入式开发中非常基础的内容。

- 打开了错误的目录；

- 命令少写了空格；
- 虚拟机 IP 发生变化；

- 烧录后没有复位；
- 串口参数不正确；
